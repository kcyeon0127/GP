## 2. US-09 What-if 시나리오 조정·비교

### 2.1 User Story

- As a 소상공인 대표자로서
- I want 정산 지연, 매출 감소, 원가 상승, 금리 상승 조건을 바꿔 기준안과 잔액 곡선을 비교할 수 있다
- So that 조건이 나빠졌을 때 언제, 얼마나 부족해지는지 미리 알고 준비할 수 있다

### 2.2 동작 규칙

| 조건 | 입력 | 적용 규칙 |
|---|---|---|
| 정산 지연 | 매출처 1곳, 지연 일수 | 그 매출처의 입금 날짜를 지연 일수만큼 뒤로 이동. 12주 밖으로 밀린 입금은 계산 구간에서 제외 |
| 매출 감소 | 감소율(%) | 모든 매출 입금 금액을 감소율만큼 축소 |
| 원가 상승 | 상승률(%) | 매입처 지급 금액만 상승률만큼 증가. 고정비·대출 상환은 유지 |
| 금리 상승 | 상승폭(%p) | 변동금리 대출 월 상환액에 대출 잔액 × 상승폭 ÷ 12 가산. 고정금리 대출은 유지 |

- 조건은 하나 이상 골라 함께 적용 (조합 가능)
- 원본 일정을 복사한 시나리오 원장에 적용 → US-03과 같은 계산 모듈로 12주(84일) 날짜별 잔액 재계산
- 금액은 원 단위 반올림
- 원본 cash_event와 기준안 forecast_run은 변경 없음. 시나리오 결과는 scenario_id가 붙은 forecast_run으로 저장
- 홈 조기경보는 scenario_id 없는 실행만 사용 (시나리오 결과가 홈 경보에 섞이지 않음)
- 비교 시 기준안도 현재 등록 일정으로 다시 계산 (같은 일정끼리 비교)
- 새 부족 지급 = 기준안에서는 그날 잔액이 0원 이상이었는데 시나리오에서 0원 미만이 되는 지급. 기준안에서도 부족했던 지급은 제외

### 2.3 입력 범위

| 항목 | 허용 범위 | 범위 밖 |
|---|---|---|
| 지연 일수 | 1~60일 | 실행 안 함, 범위 안내 (422) |
| 매출 감소율 | 0 초과 90% 이하 | 위와 같음 |
| 원가 상승률 | 0 초과 100% 이하 | 위와 같음 |
| 금리 상승폭 | 0 초과 10%p 이하 | 위와 같음 |
| 조건 없음 | - | "조건을 하나 이상 고르세요" (422) |
| 정산 지연 대상 | 이 사업장의 매출처 | "정산을 미룰 매출처를 고르세요" (422) |

### 2.4 API

| Method | 경로 | 설명 |
|---|---|---|
| POST | /api/scenarios | 조건 적용·재계산·저장. 응답: scenario_id, kinds, base, scenario, new_shortages, changes |
| GET | /api/scenarios/{id}/comparison | 저장된 조건으로 기준안 대비 곡선·부족일 비교 |

### 2.5 화면

- 조건별 켜기·끄기와 숫자 입력, 실행 버튼 (실행마다 시나리오가 저장되므로 자동 재계산 없음)
- 기준안·시나리오 잔액 곡선 겹쳐 표시, 0원 기준선
- 새로 부족해지는 지급 목록, 변경 전후 부족일·최저 잔액
- 숫자는 화면에서 만들지 않음. 모든 계산은 백엔드 ScenarioService

### 2.6 Acceptance Criteria (제출본 그대로)

| AC ID | Given | When | Then |
|---|---|---|---|
| AC-01 (Combined) | What-if 화면 | 원가 +10%, 정산 15일 지연으로 조정 | 시나리오 잔액이 재계산되어 기준안 곡선과 함께 표시된다 |
| AC-02 (New Shortage) | 시나리오에서 새로 부족해지는 지급 존재 | 결과 확인 | 해당 지급 항목과 변경 전후 부족일이 표시된다 |
| AC-03 (4 Scenarios) | 정산 지연·매출 감소·원가 상승·금리 상승 4개 시나리오 | 각각 적용 | 4개 모두 계산 결과가 표시된다 |
| AC-04 (Sales) | 12주 매출 정산 합계 4,000만 원 | 매출 15% 감소 적용 | 12주 매출 입금 합계가 3,400만 원으로 계산된다 |
| AC-05 (Cost) | 12주 매입 지급 합계 2,000만 원 | 원가 10% 상승 적용 | 12주 매입 지급 합계가 2,200만 원으로 계산된다 |
| AC-06 (Keep Original) | 시나리오 실행 완료 | 원본 데이터와 기준안 확인 | 둘 다 바뀌지 않는다 |
| AC-07 (Range) | 지연 일수 0 입력 | 시나리오 실행 | 실행되지 않고 입력 범위 안내가 표시된다 |

### 2.7 Out of Scope

- 네 가지 밖의 조건 (환율, 세금 변화 등)
- 확률 기반 시뮬레이션
- 시나리오 자동 추천 (대응안 생성은 US-10)

## 3. US-08 위험 영향 경로 강조

### 3.1 User Story

- As a 소상공인 대표자로서
- I want 문제가 생긴 거래처에서 어느 지급과 상환까지 영향이 이어지는지 금융지도 위의 경로로 볼 수 있다
- So that 어디부터 막아야 연쇄 부족을 끊을 수 있는지 알 수 있다

### 3.2 동작 규칙

- 출발점: US-09 시나리오 결과
- 경로: 원인(시나리오가 바꾼 일정의 거래처·계약·대출) → 잔액 부족일 → 부족 구간에 걸린 지급·상환
- 원인: 부족 구간이 끝나기 전에 날짜·금액이 바뀐 일정. 같은 출처(계약·대출)는 한 단계로 묶고, 구간 끝까지 잔액이 달라진 금액을 표시
- 부족일: 시나리오 잔액이 4주(28일) 안에서 처음 0원 미만이 되는 날. 부족 구간 = 그날부터 잔액이 다시 0원 이상이 되기 전날까지
- 경로 계산: 부족 구간은 계산 모듈(US-03 같은 엔진), 지급에서 계약·거래처로 이어지는 노드는 Neo4j 그래프(US-06) Cypher 질의
- 영향받는 지급: 부족 구간 안 출금. 지급일 순, 같은 날이면 금액 큰 순으로 번호 부여
- 각 단계: 금액, 날짜, 근거 ID 표시 (근거 ID는 US-07 형식 P1, P2 … 를 원인 → 지급 순서로 부여. 부족일은 계산 결과라 ID 없음)
- 지급마다 기준안에서도 부족했던 지급인지 함께 표시
- 경로 밖 노드: 흐리게 표시
- 4주 안 부족 위험 없음: 강조 경로 없음 (빈 경로 반환)
- 시나리오 전환: 선택한 시나리오 기준 경로로 교체
- 금융지도 레이아웃: 레이더형 동심원 (돈 일정 → 거래처 → 계약). 시나리오 실행 시 계좌에서 바깥으로 1회 퍼지는 표시, 동작 줄이기 설정 시 생략 (PR #9)

### 3.3 API

| Method | 경로 | 설명 |
|---|---|---|
| GET | /api/scenarios/{id}/impact-path | 시나리오의 위험 영향 경로 (순서 번호, 단계별 금액·날짜·근거 ID, 강조할 노드). 부족 위험 없으면 빈 경로 |
| GET | /api/scenarios | 저장된 시나리오 최근 20개 (시나리오 전환용) |

### 3.4 Acceptance Criteria (제출본 그대로)

| AC ID | Given | When | Then |
|---|---|---|---|
| AC-01 (Path) | 거래처 C 정산 지연 시나리오 결과가 있음 | 금융지도 보기 | C에서 매출 계약, 부족일, 영향받는 지급까지 경로가 순서대로 강조된다 |
| AC-02 (Order) | 영향받는 지급이 3건 | 경로 보기 | 먼저 막히는 순서대로 번호가 붙는다 |
| AC-03 (No Risk) | 4주 안 부족 위험이 없음 | 금융지도 보기 | 강조 경로가 표시되지 않는다 |
| AC-04 (Step Detail) | 경로가 강조됨 | 경로의 한 단계 선택 | 그 단계의 금액, 날짜, 근거 ID가 표시된다 |
| AC-05 (Dim) | 경로가 강조됨 | 금융지도 보기 | 경로 밖 노드는 흐리게 표시된다 |
| AC-06 (Switch) | 시나리오 두 개가 저장됨 | 다른 시나리오 선택 | 그 시나리오 기준 경로로 바뀐다 |

### 3.5 Out of Scope

- 거래처끼리 이어지는 2차 파급 (데이터 없음)
- 경로 애니메이션 같은 시각 효과 (단, 시나리오 실행 시 1회 표시는 예외, 아래 변경 참고)
- 경로 기준 대응안 제안 (US-10)

### 3.6 미정 (구현 전 확정)

- "실제 경보"에서 출발하는 경로의 API 형태 (현재 API는 시나리오 ID 기준)
